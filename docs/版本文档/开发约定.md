# 开发约定

> 本文件汇总本项目协作与开发约定；工作区级 Godot 约定见 `~/app/Godot/AGENTS.md`。

## 1. 单轮开发容量评估

> 为避免「设计完 → 开发一半 → 中断 → 重新拆分」的循环，
> **每份升级说明在开发前必须包含容量评估与拆分方案**。

### 9.1 容量基准

| 项 | 经验值 |
|---|---|
| 单轮可完成 | 约 3~5 个模块改动 + 20~40 条测试断言 |
| 触及范围 | 新增/修改 300~600 行，涉及不超过 3 个既有系统 |
| 超出则拆分 | 必须拆成补丁号连续交付（1.2.2 / 1.2.3 / 1.2.4） |

### 9.2 升级说明必须回答

| 问题 | 写在哪 |
|---|---|
| 本次范围能否一轮做完 | 文档「开发评估」小节 |
| 若不能，拆几个补丁、每个补丁做什么 | 同上，列成表格 |
| 哪些项依赖后续版本 | 「依赖」小节 |

### 9.3 细化到「单一功能点」

> 一个补丁 = 一个功能点。功能点过大时继续拆，宁可版本号多，不要单版塞多个模块。

| 维度 | 单一功能点上限 |
|---|---|
| 涉及系统 | ≤ 2 个 |
| 涉及文件 | ≤ 3 个 |
| 代码量 | ≤ 150 行（不含测试） |
| 测试断言 | 5 ~ 15 条 |
| 完成判据 | 一条用户可感知的行为变化 |

**允许批量交付**：一轮内可连续做完 2~3 个**互不依赖**的功能点，
但每个功能点仍各自占一个补丁号、各自一份说明、各自一次提交。

### 9.4.1 数据管理策略：暂不使用数据库（2026-11-18 决定）

| 项 | 内容 |
|---|---|
| 当前静态数据规模 | 约 150 项（商品 28 / 建筑 8 / 海图 9 / 船只 ~30 / 装备 ~40） |
| 决策 | **暂不引入 SQLite**，继续用 Resource + 校验层 |
| 复查触发条件 | 静态数据 > 800 项，或需要 Mod / 多人 |
| 届时的替代路径 | 先 CSV 单一数据源 + 生成器；仍不够再评估 SQLite |

**评估要点**

| 维度 | 判断 |
|---|---|
| 约束能力（分类合法/引用完整） | 用校验函数即可获得，无需 DB |
| 查询能力 | 启动建索引字典，比 SQLite I/O 更快 |
| 批量编辑与 diff | 规模上去后改用 CSV 单一源，而非 DB |
| DB 的独有优势 | 外部可编辑（Mod）、事务并发（多人）、分析型查询 |
| DB 的代价 | 跨平台二进制、schema 迁移、编辑器工作流断裂 |

**扩容路线**

| 阶段 | 数据量 | 做法 |
|---|---|---|
| 现在 | ~150 | Resource + validate_defs() 校验 |
| 300+ | 中 | data/defs/*.csv 为唯一源，生成器产出资源 |
| 800+ 或 Mod | 大 | 再评估 SQLite（构建期用，运行时读内存） |

### 9.5 拆分原则

| 原则 | 说明 |
|---|---|
| 按模块边界切 | 一个补丁只动 1~2 个系统 |
| 每个补丁可独立验收 | 不做「必须配合下一个补丁才能跑」的半成品 |
| 先基础设施后表现层 | 例如先做动态港口，再做菜单差异 |
| 版本号连续 | 不跳号，不合并到下一个次版本 |
